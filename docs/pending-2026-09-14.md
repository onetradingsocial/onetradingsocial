## Done 2026-09-14: CAPTCHA is live, after a boundary bug we have hit before

Turnstile is enforcing on all four auth forms. Cloudflare **Managed** widget,
domain `app.tradingsocial.io`, site key in Vercel as
`NEXT_PUBLIC_TURNSTILE_SITE_KEY` (Production, project `onetradingsocial-app`),
secret key in Supabase → Authentication → Attack Protection. Deploy `b56eb5e`.

Turnstile needs no DNS change and no domain transfer: the hostname field is
free text, checked at challenge time. `tradingsocial.io` stays at Namecheap,
which also keeps the Resend DKIM and return-path records out of harm's way.

The order [auth-captcha.md](auth-captcha.md) prescribes is the order that
worked — site key in Vercel, redeploy, **confirm the widget renders on all four
forms**, and only then the Supabase switch. That switch covers signup, sign-in
*and* recovery, so arming it before a deploy carrying the key locks out every
password user. Rollback is the switch, never the Vercel variable.

### `NEXT_PUBLIC_` is inlined at build time, so "set the variable" is half a step

Saving it in Vercel changed nothing — the live bundle had been built without
it, and saving does not trigger a build. The redeploy has to follow, with *use
existing build cache* unticked.

The check that means something is not "the variable is set" but "the key is in
the bundle": the site key appears as a literal in the chunk each auth page
loads. Before the rebuild those chunks still read
`process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY` as a runtime lookup, which is
nothing in a browser. `/signup` was byte-identical before and after, which is
how the failed first redeploy was caught.

### The server read the token under a name that did not exist

**This is the `/admin/feedback` bug of 2026-09-04 again, in a different file.**
`CAPTCHA_FIELD` was exported from `app/_components/Turnstile.tsx`, which is
`'use client'`, and imported by `actions/auth.ts`. Across the RSC boundary that
import is a client reference, not the string, so `formData.get(CAPTCHA_FIELD)`
looked up a key that was never in the form. `captchaToken()` returned
`undefined`, and GoTrue refused every attempt with

```
400: captcha protection: request disallowed (no captcha_token found)
```

while the widget sat on the page showing a green **Success**. The browser had
solved the challenge and written the token into the form correctly throughout.
Only the server was looking under the wrong name.

**The string that localises it is `no captcha_token found`.** GoTrue
distinguishes a token that never arrived from one it received and rejected. All
eight failures were the first kind, which rules out the widget, the site key,
the secret, the hostname and the CSP in one line — and rules in our own code.
Several hours went to the browser instead: Edge tracking prevention, an
InPrivate window, a second browser, a suspected propagation delay on a
minutes-old widget. None of it mattered, and the log had said so from 07:46.

Fixed in `b56eb5e`: the constant moved to `app/src/lib/captcha.ts`, a plain
module with no directive, imported by both ends.

`tests/unit/captcha.test.ts` did not catch this and could not have: it reads
the files as text, and it **asserted the broken import line was present** —
pinning the bug in place while staying green. It now resolves every `@/` import
in `actions/auth.ts` and fails if the target module begins with `'use client'`.
Verified by putting the old import back and watching it fail. The guard written
after `/admin/feedback` covers only `app/src/app/admin`; this one covers only
the auth action. **The general case is still open.**

## P0 — both auth email templates emit PKCE links, and PKCE cannot survive the inbox

**Confirmed from the sent mail itself**, not inferred. The confirmation email
Resend delivered to a stranded account on 2026-09-11 contains:

```
https://jmpanzrjxflovdfwcbye.supabase.co/auth/v1/verify
  ?token=pkce_8a44de11…&type=signup
  &redirect_to=https://app.tradingsocial.io/auth/confirm
```

`token=pkce_…` is Supabase's default `{{ .ConfirmationURL }}` for a PKCE client.
`/auth/v1/verify` consumes the token and marks the address confirmed, then
redirects to us with `?code=…`, which `exchangeCodeForSession` can only redeem in
the browser that started the signup — the `code_verifier` lives in that browser's
cookie.

**The password-reset template is the same shape** (`token=pkce_…&type=recovery`),
so the escape hatch fails identically.

`app/src/lib/auth-recovery.ts:25` already called this, and named the missing
step: we accept the PKCE shape "so the flow is not broken **before the template
is changed**". The template was never changed. The runbook,
[auth-email-smtp.md](auth-email-smtp.md), covers SMTP, the redirect allowlist and
the toggle — and never mentions the template body.

**Every `recovery` flow row in the table is also unexchanged.** Not one password
reset has completed. The failure path makes this worse rather than better:
`recoveryErrorRedirect` drops a failed grant on `/forgot-password`, so the
`bsu.edu` user clicked their link, got bounced there, and requested a reset 27
seconds later — into a link broken the same way.

Delivery is not the problem. Resend shows every one of these as `delivered`.

### The fix

Change both templates in **Authentication → Emails** to the browser-independent
shape the route already prefers (`verifyOtp`):

```
{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup
{{ .SiteURL }}/auth/reset?token_hash={{ .TokenHash }}&type=recovery
```

`&type=` is mandatory: `parseRecoveryRequest` defaults a missing `type` to
`recovery`, which is not in `/auth/confirm`'s `expectTypes` and would bounce a
new signup to `/forgot-password?error=denied`.

Dashboard-only. No code change, no deploy, no migration.
